# 개발 단위 간 수정 요청

상태: 공용 개발 절차 · 상위 규칙: AGENTS.md

## 1. 요청이 필요한 경우

- 현재 담당 이외의 개발 단위 코드를 수정해야 한다.
- TBD가 결정되었고 해당 인터페이스를 다른 개발 단위도 사용한다.
- 기존 공용 메시지·토픽·enum·QoS·시간 정책·ID·종단 동작을 변경한다.

개발 단위는 AMR, 관제, System monitor, 비전이다. 관제와 System monitor는 PC 3에서 함께 실행해도 별도 요청·검토·반영 단위다. AMR 요청에는 필요하면 robot1·robot6 적용 상태를 구분한다. 요청서 작성은 상대 코드 변경 권한이나 구현 승인을 의미하지 않는다.

미결 TBD가 있다는 이유만으로 모든 항목의 요청서를 미리 만들지 않는다. 해당 문서에서 논의하고, 구체적인 변경안 또는 결정이 생기면 요청서를 생성한다. 공유 계약에 대해 상대 변경이 필요 없다고 판단한 경우에도 확인 근거를 기록한다.

## 2. 파일명과 상태

실제 요청부터 `CR-<작성팀>_MM-DD_HH-mm_<짧은_제목>.md` 형식으로 **작성 팀과 최초 작성 시각**을 반드시 포함한다. 요청서 번호는 사용하지 않는다. 다른 문서에서 요청서를 참조할 때는 파일명 또는 상대 링크를 사용한다. 이 README는 양식이며 발행된 요청은 이 디렉터리의 개별 CR 파일로 확인한다.

- 작성 팀은 `AMR`, `비전`, `관제`, `System monitor` 중 하나로 표기한다. 대상 팀이 아니라 요청서를 작성한 팀을 사용하며, 파일명·본문 제목·요청 단위의 팀명을 일치시킨다. `System monitor`는 공백을 포함한 이름 그대로 사용한다.
- 본문 제목은 `# [<작성팀>] <제목>` 형식이다. 예: `# [관제] 토큰 계약 변경`.
- 시각은 한국 표준시(KST, UTC+09:00), 24시간제로 기록한다. 월·일·시·분은 각각 두 자리다.
- 월/일 시:분을 나타내되, Windows 파일명에서 사용할 수 없는 `/`와 `:`를 대체하여 `MM-DD_HH-mm`으로 표기한다.
- 예: 관제 팀이 9월 6일 14시 05분 작성 → `CR-관제_09-06_14-05_토큰_계약_변경.md`.
- 예: System monitor 팀이 9월 6일 14시 05분 작성 → `CR-System monitor_09-06_14-05_로그_필드_추가.md`.
- 같은 파일명이 이미 있으면 기존 요청서를 덮어쓰지 않고 짧은 제목에 대상 기능·변경 내용을 더 구체적으로 적어 구분한다.
- 본문 작성 시각은 `YYYY-MM-DD HH:mm KST`로 기록하여 연도를 구분한다.
- 후속 수정 시 최초 작성 시각과 파일명은 유지하고 변경 시각은 검토·결정 이력에 기록한다.

권장 진행 상태는 초안 → 검토 중 → 합의 → 반영 중 → 반영 완료 → 통합 검증 완료다. 보류·철회 시 사유를 기록한다. 합의는 계약 합의이며, 코드 수정은 별도의 명시적 승인 범위를 확인한다.

전체 상태와 개발 단위별 적용 상태를 따로 기록한다. 담당자가 수정했다고 보고한 사실과 통합시험으로 확인한 사실을 구분한다.

## 3. 작성 양식

## 4. 완료 기준

기준 기능·인터페이스 문서가 갱신되고, 영향받는 모든 단위가 반영 또는 변경 불필요를 확인하고, 관련 통합시험 결과가 기록되면 완료 처리한다. 시험이 미실행이면 '통합 검증 완료'로 표시하지 않는다. 해결한 TBD ID는 이 요청서를 링크하고 재사용하지 않는다.

## 5. Git 공동 관리와 충돌 처리

Git은 파일 경로와 내용을 병합한다. `change_requests/` 폴더를 여러 팀이 공유한다는 사실만으로 충돌하지는 않는다. 서로 다른 이름의 요청서를 추가하는 경우는 보통 함께 병합되지만, 동일 경로에 서로 다른 파일을 만들거나 같은 요청서의 같은 부분을 수정하면 충돌할 수 있다. 충돌 표시가 없어도 서로 다른 요청서가 상반된 계약을 제안하는 내용상 충돌은 별도로 검토한다.

- 요청 하나당 파일 하나를 사용한다. 이 README는 공용 규칙·양식으로 유지하고 요청 추가 때마다 목록·순번·전체 진행표를 갱신하지 않는다. 요청 상태는 개별 요청서에 기록한다.
- 작업 시작과 병합 전에 공유 브랜치의 최신 변경을 확인하고, 프로젝트의 Git 병합 방식에 따라 반영한다. 서로 다른 PC에서 동시에 생성한 동일 파일명은 로컬 파일 존재 확인만으로 예방할 수 없다.
- 파일명이 겹치면 양쪽 요청 내용을 확인한다. 같은 요청은 합의하여 통합하고, 별개 요청은 제목을 구체화해 한쪽 파일명을 구분한 뒤 관련 링크를 함께 수정한다. 이는 최초 작성 후 파일명 유지 규칙의 충돌 해결 예외이며, 최초 작성 시각을 보존하고 변경 이유를 이력에 남긴다.
- 같은 요청서를 여러 팀이 수정할 때는 요청 팀이 본문·전체 상태를 조정하고 각 팀은 자신의 반영 상태·검토 의견을 중심으로 작성한다. 충돌 해결 시 한쪽 파일 전체를 선택하여 다른 팀의 기록을 지우지 않는다.
- 병합 후 요청서 링크, 팀별 상태, 관련 interfaces.md·기능 문서의 계약 일치 여부를 확인한다. 공용 문서 변경은 영향 팀과 함께 검토한다.
