## 확인된 미연결 입력

`patrol_amr/mission_state.py`의 MissionStateSnapshot과 `mission_status_store.py`의 schema_version=1에는 operational_state·docking_state·scan_state가 없다. safety 쪽 MissionStatusBridge는 mission 상태를 읽지만 나머지 두 enum 축에 값을 전달받지 못한다. 따라서 RobotStatus의 operational_state와 docking_state는 UNKNOWN, scan_state는 빈 문자열로 남는다. 기존 자동시험이 통과했어도 이 세 입력의 실연결 완료를 의미하지 않는다.

## 제안과 요청 작업

1. mission 담당이 운영·도킹 축의 실제 입력 주체와 기존 enum에 대한 전이 조건을 정리한다. 순찰 중이라는 사실만으로 MOVING을, 배터리 충전만으로 DOCKED를 추정하지 않는다.
2. 확정된 축을 mission snapshot에 넣을지 별도 기존 입력을 사용할지 합의한다. snapshot 확장 시 schema 호환성·구버전 처리·재시작·revision·원자 갱신 방법을 같이 정한다.
3. 합의 후 mission 담당이 생산 코드를 반영하고, safety 담당이 MissionStatusBridge와 RobotStatus 변환·Q-02 변경 발행을 연결한다.
4. scan_state 상세 계약은 TBD-IF-003을 따르며 새 문자열을 임의로 추가하지 않는다.

## 영향·완료 조건

공용 RobotStatus 레이아웃·enum을 유지한다면 관제·System monitor 코드 변경은 불필요할 것으로 판단한다. 다만 실제 코드 대조·상대 확인 전에는 합의 완료로 처리하지 않는다. 기존 UNKNOWN을 측정된 상태로 채우는 것은 운영 판단에 영향을 주므로 전이 조건을 먼저 확정한다. 합의 전에는 현재 UNKNOWN과 빈 문자열을 유지한다.

검증은 각 축 변화가 독립적으로 반영되는지, 잘못된 snapshot이 기존 상태를 손상시키지 않는지, 재시작 후 최신 revision과 ID가 유지되는지, 실제 ROS에서 Q-02 발행 주기를 지키는지 확인한다. 자동시험 계획이며 이번 요청서 작성으로 구현·시험 완료 처리하지 않는다. 실제 mission·로봇 연결 시험은 별도로 남긴다.
